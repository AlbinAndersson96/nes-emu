# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A NES emulator written in Rust. The CPU (full 6502 instruction set including unofficial opcodes), a full PPU (background rendering, sprites, palette, scrolling, OAM DMA), the full APU (all five channels plus frame counter), and fifteen mappers — 0 (NROM), 1 (MMC1), 2 (UxROM), 3 (CNROM), 4 (MMC3, including the A12-clocked scanline IRQ counter), 7 (AxROM), 9 (MMC2) and 10 (MMC4) with their automatic CHR bank latches, 11 (Color Dreams), 34 (BNROM + NINA-001), 66 (GxROM), 69 (Sunsoft FME-7, including its CPU-cycle IRQ counter; 5B expansion audio not modeled), 71 (Camerica), 87 (Jaleco CHR), and 206 (Namco 118 / DxROM) — are implemented. All 159 blargg CPU ROM tests pass: all 17 `instr_test-v5` tests, `instr_timing`, all 5 `instr_misc` tests, and all of `cpu_interrupts_v2` (tests 1-5 plus the combined suite). All 26 wired blargg APU ROM tests pass too: `apu_test` (9), `apu_reset` (6), and `blargg_apu_2005.07.30` (11). See Known gaps for the remaining PPU test failures.

## Commands

```bash
cargo build          # compile
cargo run <rom.nes>  # run a ROM (dev profile is opt-level 1 so it holds 60fps; --release is fastest)
cargo test           # run all tests (includes blargg ROM tests in tests/roms/)
cargo test <name>    # run a single test by name
cargo clippy         # lint
cargo fmt            # format
```

- **`build.rs`** — seeds `keybindings.toml` (copied from `assets/keybindings.toml`) next to the compiled binary on first build; never overwrites an existing copy, so user edits survive rebuilds.

## Module structure

- **`src/cpu/mod.rs`** — `Cpu` struct, register file, micro-op queue, `tick()` entry point. The `Bus` trait (`fn read(&mut self, u16) -> u8` / `fn write(&mut self, u16, u8)`) is defined here. `tick()` executes exactly one micro-op from the queue; when the queue empties a new instruction is decoded (via `RunInstruction`) or an interrupt is serviced. IRQ is level-sensed: `SystemClock` sets `irq_pending` when `tick_apu` reports the line high and clears it (`Cpu::irq_deassert`) when the line goes low, so a source cleared mid-instruction (e.g. an implied op's `$4015` dummy read clearing the frame-IRQ flag) is not still pending at the next dispatch — masked IRQs neither accumulate nor survive their own clear.
- **`src/cpu/instructions.rs`** — `execute()` dispatcher; one match arm per opcode including all unofficial opcodes (LAX, SAX, DCP, ISB, SLO, SRE, RLA, RRA, SHA, SHX, SHY, TAS, ANC, ALR, ARR, XAA, LAS, KIL/JAM).
- **`src/system.rs`** — `SystemClock`: the shared per-tick stepping loop (CPU tick or DMA stall cycle, then per-cycle PPU/APU ticking) carrying the blargg-verified interrupt-delivery rules: deferred NMI edges (an edge on a tick's last cycle is delivered one tick later), last-cycle IRQ flagging (`Cpu::irq_on_last_cycle`, needed for the taken-branch last-clock ignore), and DMA interrupt deferral (interrupts first asserting during a DMA stall are delivered at DMA end with one dispatch poll suppressed). Used by BOTH the real run loop (`App::step_frame`) and the ROM test harness — change it in one place only.
- **`src/bus.rs`** — `Bus` struct implements `CpuBus`. Wires RAM, PPU, APU, controllers, and cartridge into the 16-bit address space. Exposes `bus.ppu` and `bus.apu` publicly. `tick_apu(cycles)` advances the APU and returns the current IRQ line level — the OR of the APU line and the cartridge mapper's IRQ line (`Cartridge::irq_pending`, e.g. the MMC3 scanline counter), both level-triggered.
- **`src/apu/mod.rs`** — `Apu` struct: orchestrates all five channels, the NTSC frame counter (4-step / 5-step modes), and the audio mixer. `tick(cpu_cycles)` drives the frame counter and channel timers, then returns `take_irq()` which yields the live IRQ line level (`frame_irq_flag && !irq_inhibit || dmc.irq_flag`) without consuming anything. Reading `$4015` clears `frame_irq_flag`; writing `$4017` with bit 6 set (irq_inhibit) also clears it.
- **`src/apu/pulse.rs`** — Pulse channel with duty cycle sequencer, length counter, envelope, and sweep unit.
- **`src/apu/triangle.rs`** — Triangle channel with linear counter and length counter.
- **`src/apu/noise.rs`** — Noise channel with 15-bit LFSR (mode 0: bit 1 feedback, mode 1: bit 6 feedback), length counter, and envelope.
- **`src/apu/dmc.rs`** — Delta-modulation channel: streams 1-bit delta-PCM from CPU memory. Signals DMA need via `needs_dma()` / `dma_address()`; caller supplies the byte via `supply_dma_byte()`. The 4-cycle CPU stall is implemented in `Bus::tick_dma()`.
- **`src/apu/envelope.rs`** — Shared envelope generator (used by pulse and noise).
- **`src/apu/length.rs`** — Length counter lookup table and `LengthCounter`, including the write-cycle-exact pending-write machinery (`WRITE_EFFECT_DELAY`) for halt-bit and length-reload writes — see the length-counter design note below before touching it.
- **`src/apu/sweep.rs`** — Sweep unit (used by pulse channels; pulse 1 uses ones-complement negation, pulse 2 uses twos-complement).
- **`src/ppu/mod.rs`** — Full `Ppu` implementation. Dot/scanline-accurate NTSC timing (341 dots × 262 scanlines). Implements all CPU-visible registers ($2000–$2007, $4014), the Loopy v/t/x/w scroll registers, background tile pipeline (nametable + attribute + CHR fetches into 16-bit shift registers), sprite evaluation and pattern fetch for up to 8 sprites per scanline, sprite-0 hit, priority multiplexer, palette RAM (32 bytes), NMI edge detection, and OAM DMA write helper. Outputs a 256×240 frame buffer of NES palette indices. Also reports PPU address-bus values to the mapper via `notify_ppu_bus` → `Cartridge::ppu_bus_addr` (rendering fetch addresses at calibrated dots, $2006/$2007-driven changes) — this drives the MMC3 A12 IRQ counter; see the MMC3 note under Key design notes before touching those dots.
- **`src/renderer.rs`** — `Renderer` wraps a `winit` window and renders via `egui`/`egui-wgpu` (`egui_wgpu::winit::Painter`). The NES framebuffer is uploaded each frame as an `egui::TextureHandle` and drawn via a `CentralPanel`; the `present()`/`present_placeholder()` methods just update that texture and call `window.request_redraw()` — actual GPU submission happens in `main.rs`'s `WindowEvent::RedrawRequested` handling (see `Renderer::redraw`). `maybe_configure_wsl2_gpu()` in `main.rs` sets `WGPU_BACKEND=vulkan` and points `VK_ICD_FILENAMES` at the Mesa LLVMpipe ICD when running under WSL2.
- **`src/cartridge.rs`** — iNES parser and all fifteen `impl Mapper`s. The `Mapper` trait exposes `prg_offset`/`write_prg`, `chr_offset`, a dynamic `mirroring` override, a `ppu_bus_addr` PPU-bus-change hook (MMC3 A12 IRQ clocking; MMC2/MMC4 CHR latch), a `write_prg_ram` hook for registers that live in the $6000–$7FFF window (NINA-001, mapper 87), a `tick_cpu` hook for CPU-cycle-clocked timers (FME-7 IRQ), and `irq_pending`. MMC1 implements the full 5-bit serial shift register protocol and all four PRG bank modes (32 KB switch, fix-first, fix-last). UxROM is switchable 16 KB PRG at $8000 + fixed last bank at $C000; CNROM is fixed PRG + 8 KB CHR bank select; AxROM is switchable 32 KB PRG + write-selected single-screen mirroring (bus conflicts not modeled on any of them). MMC3 implements the $8000-$E001 even/odd register pairs (PRG/CHR banking, mirroring control, IRQ latch/clear/disable/enable) and the A12-clocked IRQ counter with the "new"/sharp revision semantics (counter==0 → reload from latch, else decrement; IRQ when the result is 0 and IRQs enabled); $A001 PRG-RAM protection is not modeled — PRG-RAM stays enabled so the blargg $6000 result protocol always works. The newer mappers: **MMC2 (9) / MMC4 (10)** share a `PxLatch` — the PPU fetching tile $FD or $FE flips that pattern table's CHR bank latch (detected by tile number in `ppu_bus_addr`, robust to the low-/high-plane fetch distinction) — differing only in PRG layout (MMC2 = 8 KB switch + last-three fixed; MMC4 = 16 KB switch + last-16 KB fixed). **Color Dreams (11)** and **GxROM (66)** are 32 KB-PRG + 8 KB-CHR discrete logic (different bit fields). **BNROM/NINA-001 (34)** are one mapper number for two boards, disambiguated by CHR-ROM presence (BNROM = 32 KB PRG switch + CHR-RAM; NINA-001 = $7FFD/$7FFE/$7FFF registers via `write_prg_ram`). **FME-7 (69)** is a command/parameter register pair with 8×1 KB CHR banks, 3 switchable + 1 fixed 8 KB PRG banks, four mirroring modes, and a 16-bit CPU-cycle down-counter IRQ (via `tick_cpu`; the borrow out of bit 15 asserts); its 5B expansion audio is not modeled (no audio-output path exists yet). **Camerica (71)** is UxROM-like with an optional BF9097 single-screen mirroring register. **Jaleco CHR (87)** selects an 8 KB CHR bank from a bit-swapped $6000–$7FFF write. **Namco 118/DxROM (206)** is the pre-IRQ MMC3 ancestor (same $8000/$8001 register pairs, no IRQ/A12/PRG-mode/CHR-invert bits, header mirroring). 8 KB PRG-RAM at $6000–$7FFF is always present regardless of the iNES header flag, because blargg test ROMs write their results there unconditionally. Mapper CHR banking also applies to CHR-RAM (folded mod 8 KB).
- **`src/input.rs`** — `KeyMap`: maps keyboard `KeyCode`s to (controller port, button bit) pairs, loaded from a TOML config file at startup (`KeyMap::load`) or a hardcoded fallback (`KeyMap::default`). Button bit order matches the NES's real serial order (A, B, Select, Start, Up, Down, Left, Right). The optional `[app]` section holds the non-controller keys — `fps_toggle`, `save_state`, `load_state`, and the ten-key `slots` array — each independently defaulted (an old file missing any of them still parses).
- **`src/savestate.rs`** — full-machine save states with ten numbered slots (number keys 0-9 select the active slot, shown in the window title; F5 saves / F9 loads it — slot 0 = `<rom>.state`, slots 1-9 = `<rom>.stateN`; the File menu's Save/Load State… items save to/load from any path via a dialog). `save`/`load` serialize the `Cpu`/`Ppu`/`Apu`/`Bus`/`SystemClock` (all `#[derive(Serialize, Deserialize)]`) plus the cartridge's *mutable* state (PRG-RAM, CHR-RAM, mapper registers) via `bincode`; the ROM and PPU framebuffer are skipped and reconstructed on restore. The `Box<dyn Mapper>` trait object is round-tripped through the object-safe `Mapper::state_save`/`state_load` methods (the `mapper_state_serde!` macro in `cartridge.rs`) rather than serialized directly. `save` serializes a tuple of references to avoid cloning the non-`Clone` cartridge. Two serde array adaptors (`byte_arr`, `boxed_byte_arr`) cover fixed byte arrays larger than serde's built-in `[T; 0..=32]` derive. See `docs/savestate.md`.
- **`src/tests/mod.rs`** — test tree root; splits the tests into two groups, `unit` (white-box, reaches into crate internals) and `integration` (whole-ROM harnesses). Both are `#[cfg(test)]`-gated (declared via `#[cfg(test)] mod tests;` in `main.rs`), so none of it compiles into the shipping binary.
- **`src/tests/unit/mod.rs`** — declares the unit-test modules and defines `TestBus`: flat 64 KB address space used by CPU tests (no mirroring, no side effects), with a per-access `(address, is_write)` trace for cycle-accuracy assertions.
- **`src/tests/unit/bus.rs`** — bus unit tests.
- **`src/tests/unit/cartridge.rs`** — mapper unit tests against synthetic in-memory iNES images, for the mappers with no blargg ROM suite in tests/roms/ (UxROM/AxROM plus mappers 9/10/11/34/66/69/71/87/206). `build_banked` fills each 8 KB PRG bank / 1 KB CHR page with its own index, so a read at any bus address reveals exactly which physical bank/page it maps to at any banking granularity; the MMC2/MMC4 tests drive the CHR latch by calling `Cartridge::ppu_bus_addr` with tile-$FD/$FE pattern addresses, and the FME-7 test drives its IRQ counter via `Cartridge::tick_cpu`.
- **`src/tests/unit/cpu.rs`** — CPU unit tests.
- **`src/tests/unit/ppu.rs`** — PPU unit tests.
- **`src/tests/integration/mod.rs`** — declares the whole-ROM harness modules. Each boots a `.nes` image through the real `Bus`/`Cpu`/`SystemClock` and asserts the ROM's own verdict.
- **`src/tests/integration/roms.rs`** — harness for every blargg suite using the $6000 result protocol. Polls $6000/$6001–$6003 for test completion; steps the machine via the shared `SystemClock` (`src/system.rs`), which carries all the per-cycle interrupt-delivery rules; handles status $81 (ROM requests a delayed warm reset, used by `cpu_reset`); asserts status 0 on completion — a nonzero status fails the test with the ROM's code and text. Covers `instr_test-v5`, `instr_timing`, `instr_misc`, `cpu_interrupts_v2`, `instr_test-v3`, `nes_instr_test`, `cpu_dummy_writes`, `cpu_exec_space`, `cpu_reset`, `oam_read`, `oam_stress`, `ppu_open_bus`, `ppu_vbl_nmi`, `ppu_read_buffer`, `apu_test`, `apu_reset`, `mmc3_test`, and `mmc3_test_2` (the last two minus their rev-A/MMC6 ROMs — see Known gaps). ## Key design notes

**PPU ticking**: The run loop (and test harness) must call `bus.tick_ppu(delta)` after every `cpu.tick()`. It returns `true` when an NMI edge is detected; the caller should then call `cpu.nmi()`. Without this, `$2002` always returns 0 and the blargg test framework loops forever waiting for VBlank. Use `SystemClock::step` (`src/system.rs`) instead of hand-rolling this — it also implements the deferred-edge and DMA rules.

**APU ticking**: `bus.tick_apu(...)` must also be called after every `cpu.tick()` (the test harness ticks it one cycle at a time). It returns `true` when the APU's IRQ line is currently asserted; the caller should then call `cpu.irq()` — or `cpu.irq_on_last_cycle()` when the line first asserts on an instruction's final cycle (needed for the taken-branch last-clock IRQ ignore) — and `cpu.irq_deassert()` when `tick_apu` returns `false` (the line went low). The APU IRQ line is level-sensed: it stays asserted until `frame_irq_flag` is cleared (by reading `$4015` or writing `$4017` with bit 6 set). Because `tick_apu` is called every cycle and the line is both asserted AND withdrawn per level, a masked IRQ neither accumulates nor lingers past its own mid-instruction clear (AccuracyCoin's Implied Dummy Reads: an injected CLI's `$4015` dummy read clears the frame IRQ, and the previously-latched line must not still fire a deferred interrupt). Note `bus.tick_apu` internally repays the 4-cycle pre-advance done by `$4015` reads.

**APU power-up and warm-reset state**: hardware acts as if `$00` were written to `$4017` 9-12 clocks before the first instruction executes (blargg's `apu_reset/4017_timing` prints the effective delay; a real NES usually shows 9, ours lands at 9/8 for power/reset). Modeled by `POWER_FRAME_DELAY` (`src/apu/mod.rs`): `Apu::new` starts with `frame_reset_delay = POWER_FRAME_DELAY`, shifting only the frame-sequence phase — never `cycle_count`, so the DMA/get-put parity calibrations are untouched. On warm reset (`Apu::warm_reset`, reached via `Bus::warm_reset`, called by the ROM harness alongside `Cpu::warm_reset`): `$4015` is cleared (all five channels disabled → length counters/DMC bytes-remaining zeroed), both IRQ flags clear, and `$4017` is rewritten with the last value written to it (`Apu::last_4017`) — with the same start delay. Everything else (triangle phase, envelopes, `cycle_count`) is untouched. Verified by all 6 `apu_reset` ROMs.

**Length-counter halt/reload writes are write-cycle-exact**: a halt-bit or length-reload write landing on the exact half-frame length-clock cycle takes effect just *after* that clock (blargg 2005: "write to halt flag is delayed by one clock"), and a reload landing on the clock cycle is ignored entirely when the counter was nonzero before clocking. Implemented as pending-write slots in `LengthCounter` (`schedule_halt`/`schedule_load`), applied by `end_cycle` — called from `Apu::tick_one` after the frame-counter events — `WRITE_EFFECT_DELAY` (= 5) ticks after `Apu::write` queues them: 4 ticks to the store's real bus-write cycle (the same "+4" the `$4017` frame-reset delay accounts for) plus blargg's one-clock effect delay. 5 is the unique value passing `blargg_apu_2005.07.30`'s `10.len_halt_timing` + `11.len_reload_timing`, which bracket the effect cycle from both sides; the triangle's linear-counter aspect of `$4008` deliberately stays immediate (nothing pins its sub-cycle timing).

**MMC3 A12 IRQ clocking**: The MMC3 scanline counter clocks on PPU address-bus A12 rising edges, filtered by a minimum A12-low time (`A12_FILTER_DOTS`, `src/cartridge.rs`). The PPU reports bus addresses to the mapper at specific dots: background pattern events on each tile group's last dot (dots 8, 16, …, 256, 328, 336), sprite pattern events on each slot's last dot (264+8k, emitted for all 8 slots — empty slots report the hardware's dummy tile-$FF address), nametable/attribute lows at their fetch dots plus dummy-NT events at dots 337/339, and $2006/$2007-driven changes (including the post-increment address) as they happen. These dots and the filter threshold were calibrated as a set against blargg's `mmc3_test/4-scanline_timing` (which brackets the IRQ moment to 1 PPU dot in both `$2000=$08` and `$2000=$10` modes) — don't move any of them independently. Notification is deliberately decoupled from data fetching (`Ppu::notify_ppu_bus` vs `ppu_read`); the mapper IRQ line reaches the CPU through `Bus::tick_apu`'s return value, OR'd with the APU line. The counter semantics are the "new"/sharp revision — the rev-A ROMs (`mmc3_test/6-MMC6`, `mmc3_test_2/rom_singles/6-MMC3_alt`, `mmc3_irq_tests/5.MMC3_rev_A`) are deliberately not wired into the harnesses because they're mutually exclusive with the rev-B ROMs that are.

**Mapper integration hooks (`write_prg_ram` / `tick_cpu` / `ppu_bus_addr`)**: three ways a mapper reaches into the machine beyond plain PRG/CHR address translation. (1) `Cartridge::write` calls `Mapper::write_prg_ram` on every $6000–$7FFF write *in addition to* storing the PRG-RAM byte (both the RAM and the register see the write on hardware) — this is how NINA-001's $7FFD–$7FFF and mapper 87's whole-window CHR registers latch. (2) `Bus::tick_apu` calls `Cartridge::tick_cpu(cpu_cycles)` once per CPU cycle — `tick_apu` is invoked exactly once per CPU cycle in both `SystemClock`'s normal per-cycle loop and its DMA-stall loop, so this counts real CPU cycles one-for-one — driving the FME-7's 16-bit down-counter IRQ (borrow out of bit 15 asserts). Do not add per-cycle mapper work anywhere else; `tick_apu` is the single per-cycle spot, and its APU pre-advance/repay accounting (see the DMC notes) does NOT call `tick_apu`, so the mapper clock stays unpolluted. (3) `ppu_bus_addr` (already used for MMC3 A12) also feeds the MMC2/MMC4 CHR latch: it keys on the tile number `(addr >> 4) & 0xFF` of any pattern-table address (< $2000), so it fires correctly whether the notified fetch is the low- or high-plane address, and ignores nametable/attribute/$2006 addresses.

**DMC DMA cycle accuracy**: DMC DMA is serviced synchronously, mid-instruction, inside `CpuBus::read` (`Bus::maybe_dmc_dma`): a request that asserted on an EARLIER cycle halts the current read (hardware RDY sampling — never the assert cycle itself, never a write cycle), performs 2–3 side-effecting dummy re-reads of the in-flight address plus the sample fetch, and reports the stolen cycles to the CPU via `CpuBus::take_dma_stall_cycles` (drained into `Cpu::cycles` at every `Cpu::tick` exit point, so `SystemClock` ticks the PPU/APU for them automatically). Detection uses a DMC-only real-time clock (`Apu::dmc_tick_realtime`, one tick per bus access) with a `dmc_debt` counter so the post-hoc `Apu::tick_one` never double-clocks the channel. Calibrated constants (all swept against AccuracyCoin page 13; see `docs/accuracycoin_outcome.md`): `DMC_DMA_ALIGNED_PARITY = true` (3- vs 4-cycle stall from `Apu::dmc_realtime_current_parity()` — the live phase, NOT the instruction-start-stale `cycle_parity()`), `DMC_LOAD_DMA_DELAY = 3` (enable-started load DMAs halt no earlier than the 4th cycle after the $4015 write; reload DMAs are not delayed). Channel-timer clocking is anchored to the free-running `cycle_count` — never `frame_cycles`, which resets on $4017 writes and would flip the get/put phase. The real-time clock assumes one bus access per CPU cycle; JSR, RTS, RTI, PLA, and PLP now each perform exactly the real hardware-documented bus-access sequence for every cycle (fixed via `src/tests/unit/cpu.rs`'s `*_bus_access_sequence` tests — see "Hardware cycle-by-cycle accuracy" below), closing the JSR/RTS-heavy-code drift that used to affect most of the AccuracyCoin DMA cluster. (The `Implied Dummy Reads` test — whose "Test 5" executes code fetched from open bus, timing a DMC DMA so its fetched byte becomes the "opcode" at an APU register address — used to hang here, but that turned out NOT to be a DMA-during-JSR precision issue: it was a set-only `irq_pending` latch surviving a mid-instruction frame-IRQ clear. Fixed in Session 14 — see the level-sensed-IRQ note above and `docs/accuracycoin_outcome.md`.)

**Hardware cycle-by-cycle accuracy (JSR/RTS/RTI/PLA/PLP + taken branches)**: real 6502 hardware drives the address bus on every cycle of every instruction, including cycles whose result is discarded ("internal operations") — there is no such thing as a cycle with no bus access. `src/cpu/instructions.rs`'s `jsr`/`rts`/`rti` functions and the `0x68`(PLA)/`0x28`(PLP) match arms perform an explicit dummy `bus.read` for each such cycle (a `$0100|SP` stack peek for RTS/RTI/PLA/PLP's "increment/decrement S" cycle, plus RTS's cycle-6 read of the popped target address before the final `+1`; JSR was also reordered to fetch its high operand byte *last*, matching hardware — previously both operand bytes were fetched up front, before the two pushes). A **taken branch** likewise dummy-reads the byte following the operand (the pre-branch PC) on T3 while the offset is added to PCL, and — on a page cross — dummy-reads the page-wrong address `(old PCH : new PCL)` on T4 before PCH is fixed (`branch()` + `MicroOp::BranchPageFix`; AccuracyCoin Branch Dummy Reads codes 4/5). This matters beyond DMC DMA: it's also what makes the CPU open-bus latch (`Bus::cpu_open_bus`) hold the right value after these instructions. `src/tests/unit/cpu.rs`'s `jsr_bus_access_sequence`, `rts_bus_access_sequence`, `rti_bus_access_sequence`, `pla_bus_access_sequence`, `plp_bus_access_sequence`, `pha_bus_access_sequence` (a regression check — PHA/PHP needed no fix), `branch_taken_bus_access_sequence`, and `branch_taken_pagecross_bus_access_sequence` assert the exact `(address, is_write)` sequence via `TestBus.trace`. BRK needed no fix either — its interrupt-sequence micro-ops (`PushPcHi`/`PushPcLo`/`PushP`/`VectorFetch`/`VectorFetchHi`, `src/cpu/mod.rs`) already perform one real bus access per cycle.

**OAMADDR reset during sprite fetch**: `Ppu::fetch_sprites`'s `dot == 257` branch sets `oam_addr = 0` — the documented nesdev hardware quirk that OAMADDR ($2003) is forced to 0 during ticks 257-320 of every visible/pre-render scanline while rendering is enabled. Without it, a stale nonzero OAMADDR left over from earlier CPU code makes the next `$4014` OAM DMA (which always copies all 256 bytes, wrapping from whatever OAMADDR it starts at) land "sprite 0" — OAM bytes 0-3, which hit-detection/rendering always read regardless of where the DMA started — on the wrong wrapped source bytes. `Ppu::oam_addr()`/`Ppu::oam_byte()` (`pub(crate)`, mirroring `nt0_tile()`) are the test accessors; `src/tests/unit/ppu.rs`'s `oam_addr_resets_to_zero_during_sprite_fetch_when_rendering`, `oam_addr_untouched_by_sprite_fetch_window_when_rendering_disabled`, and `oam_dma_after_sprite_fetch_reset_lands_sprite_zero_at_oam_zero` cover it. This one fix moved 5 AccuracyCoin tests to a clean pass and 7 more past their shared "Sprite Zero Hits should be working" prerequisite (see `docs/accuracycoin_outcome.md`'s "Session 3").

**$2007 access during rendering uses the glitch increment, not `vram_increment()`**: a $2007 read or write while rendering is enabled, on a visible or pre-render scanline, doesn't apply the normal PPUCTRL-mode-bit +1/+32 increment at all — hardware instead triggers the same coarse-X-increment + Y-increment pulse the background fetch pipeline itself uses, regardless of which dot the access lands on. `Ppu::advance_v_after_ppudata_access()` (called from both the `read_register`/`write_register` `7 =>` arms, replacing the old unconditional `vram_increment()` call) checks `rendering_enabled() && (scanline <= 239 || scanline == PRERENDER_SCANLINE)` and calls `increment_coarse_x()` + `increment_y()` when true. `Ppu::v()` (`pub(crate)`) is the test accessor; `src/tests/unit/ppu.rs`'s `ppudata_read_during_rendering_uses_coarse_x_and_y_glitch_increment` and its write/negative siblings assert the exact `v += $1001` AccuracyCoin's "$2007 Read w/ Rendering" test comment specifies (see `docs/accuracycoin_outcome.md`'s "Session 4"). Distinct from the still-open `ALE + Read`/`Hybrid Addresses` tests, which are about a $2007/$2006 access *substituting the CPU address for the background pipeline's own fetch address* on that dot — not just glitching the post-access increment.

**Sprite evaluation is seeded from OAMADDR, not hardcoded to start at OAM index 0**: hardware's per-scanline sprite-evaluation OAM byte pointer starts at whatever `$2003` currently holds (a CPU write to it between the previous scanline's dot-257-320 reset and this scanline's dot 65 sticks), and walks byte-by-byte: `+1` per byte while copying an in-range sprite, `+4` then `& $FC` to skip-and-realign past an out-of-range one — this is how "misaligned OAM" happens on real hardware. `Ppu::evaluate_sprites` now drives its non-overflow phase via `eval_addr: u8` (the actual walked byte pointer, seeded from `oam_addr` at dot 65) instead of `eval_n*4`; `eval_n` becomes a pure "objects decided this scanline" counter, decoupled from addressing, whose `==0` check is what correctly identifies "sprite zero" — not literal OAM index 0, but whichever object evaluation examines *first* this scanline (if that first object is out of range, no sprite zero exists at all that scanline, regardless of what a later object finds and puts in secondary OAM slot 0). At the moment secondary OAM fills (the 8th accept), `eval_n`/`eval_m` are reconciled from `eval_addr` so the existing, blargg-verified buggy overflow-scan diagonal walk (unchanged) picks up from the right place. `src/tests/unit/ppu.rs`'s `sprite_evaluation_starts_at_oamaddr_not_always_oam_index_zero` and two siblings cover it — note the first attempt at two of these tests passed even against the old buggy code, since the test data didn't distinguish "walks from OAMADDR" from "always starts at 0, but coincidentally reaches the same bytes"; they needed explicit marker bytes that only match under correct addressing to be a real RED/GREEN test.

**$2004 reads while rendering return the internal OAM data bus (`oam_buffer`), not `oam[oam_addr]`**: on a visible/pre-render scanline with rendering enabled, the sprite pipeline is driving the OAM data bus every dot, so a $2004 read returns whatever it last latched — NOT the CPU-visible OAMADDR byte (AccuracyCoin "$2004 Stress"). `Ppu::oam_buffer` (`src/ppu/mod.rs`) is driven per-dot: `$FF` during the dot-1-64 secondary-OAM clear window; the primary-OAM byte evaluation reads each odd dot (attribute bytes masked via `oam_read_bus`, held across the even dot); the post-eval idle walk (odd = `OAM[(n mod 64)*4]`, even = the open secondary slot, which holds the last **rejected-Y write-through**); the overflow scan's diagonal (odd) alternating with secondary-OAM[0] (even, gated on `eval_overflow_started`); and the sprite-fetch window's per-slot Y/tile/attr/X-times-5 reads. Attribute masking is applied when WRITING into secondary OAM (bits 2-4 unused by rendering) so occupied slots read back masked and cleared slots read back `$FF`. The $2004 read also gets the $2002-style 8+1-dot read-cycle pre-advance (`src/bus.rs`) so it samples the T4 dot. Outside rendering the read still returns `oam_read_bus(oam_addr)`. This model passes `$2004 Stress`'s test 2 (AnswerKey1); test 3 (AnswerKey2) is blocked by the +3-dot get/put-parity sync shift — see `docs/accuracycoin_outcome.md` Session 17, and use the `TRACE_2004_STRESS` oracle in `accuracycoin.rs` to resume. `src/tests/unit/ppu.rs`'s `oamdata_read_during_secondary_oam_clear_window_always_returns_ff`, `oamdata_read_during_evaluation_returns_oam_buffer_not_oamaddr`, and their siblings cover it.

**Sprite units are real down-counter + shifter pipelines, not X-compares**: each of the 8 sprite units has an X down-counter with two modes (`Ppu::sprite_counter`/`sprite_counting`, per AccuracyCoin's Stale Sprite Shift Registers walkthrough). "Counting" units decrement once per visible dot (1-256) — UNCONDITIONALLY, even during forced blank — and halt on the dot they're checked at 0. "Halted" units output their shifter's front bit (bit 7; h-flip pre-applied at fetch) and shift once per dot, but only while rendering is enabled — F-Blank/H-Blank freeze the shifters mid-pattern, never the counting. All units are re-armed to "counting" at dot 339 of visible/pre-render scanlines IF rendering is enabled on that dot; during F-Blank they keep their state (usually halted), which is why stale sprites are "treated as X=0" and draw the moment rendering is re-enabled, and why a reload-skipped unit can finish its pattern on a later scanline. Order within a dot: counter check/decrement → pixel output → shifter clock. Fixed AccuracyCoin's `Stale BG Shift Registers` and (with the mask-delay note below) `Stale Sprite Shift Registers`; the entire blargg sprite-hit/overflow/OAM surface stayed green through the rework.

**$2001 mask writes have two taps (write-cycle register vs delayed pipeline)**: hardware applies rendering toggles to the render pipeline 2-5 dots AFTER the write cycle (AccuracyCoin's BG Serial In walkthrough), but blargg's `10-even_odd_timing` pins the odd-frame skipped-dot decision to write-cycle timing — both are satisfied by a two-tap model. The Bus's $2001 path calls `Ppu::schedule_mask_write`, which updates `mask_raw` (the register) immediately and queues `mask` (the pipeline's tap, everything `rendering_enabled()` reads) via `pending_mask`, applied `MASK_WRITE_DELAY_DOTS` (= 3) dots later at the top of `clock_dot`. The skip decision taps `render_raw_prev_dot` (raw register, one dot early — the same sample point as before the split). The delay was swept: {3,4} is the passing window for `BG Serial In` + `Stale Sprite Shift Registers` with `10-even_odd_timing` green; 2 and 5 lose BG Serial In. Direct `Ppu::write_register(1, ..)` calls (unit tests) stay immediate and update both taps.

**Controller reads while strobed don't shift**: `$4016`/`$4017` continuously reload their shift register from the live button state while `$4016` bit 0 is held high — a read during that window returns the current A-button state directly and never advances (nothing's been shifted out yet); serial shifting only begins once strobe is released. `Bus`'s `controller_strobe: bool` field gates the `0x4016`/`0x4017` read arms (bypass the shift register, return `controller_latch[port] & 1` directly, while set); the `0x4016` write arm reloads `controller_shift` from `controller_latch` on both the strobe-on *and* strobe-off transitions (the latter captures whichever value was most recently live during the strobed window — not the stale value from when strobe first went high). `src/tests/unit/bus.rs`'s `controller_read_while_strobed_returns_latch_bit0_continuously` covers it. **KNOWN LIMIT (deliberately not attempted):** `Controller Strobing`'s own failure (AccuracyCoin code 4) needs get/put-cycle-parity awareness for `$4016` *writes* specifically — a `DEC $4016` read-modify-write performs two same-target writes one cycle apart, and whether the resulting 1-cycle strobe pulse "counts" depends on which CPU/PPU clock phase the final write lands on. Not attempted — see `docs/accuracycoin_outcome.md`'s "Session 6".

**KNOWN LIMIT (attempted and reverted): frame-IRQ-flag clear is NOT deferred to the next get cycle.** AccuracyCoin's `Frame Counter IRQ` test G expects a `$4015` read to defer the flag clear to the next "get" cycle strictly after the read, rather than clearing synchronously within the read itself. A `frame_irq_clear_pending`-based implementation was tried and both possible values of the required "which parity is get" calibration constant broke `cpu_interrupts_v2/3-nmi_and_irq` identically — a real interaction with the existing `APU_READ_PREADVANCE` mechanism (working hypothesis: its debt-repayment accounting doesn't leave the pending clear a tick to fire within the same instruction), not a wrong-constant problem. Reverted rather than risk the blargg-verified interrupt timing; needs the interaction understood, not just the constant swept, before retrying. See `docs/accuracycoin_outcome.md`'s "Session 6".

**SHA / SHX / SHY / TAS unstable-store behavior**: All five unstable high-byte stores ($93/$9F/$9B/$9C/$9E) share one model (`sh_store`, `src/cpu/instructions.rs`), matching AccuracyCoin's "behavior 1" (the common NES CPU — its UnOp tests distinguish four manufacturer variants): the value stored is `reg & (base_hi + 1)` (reg = A&X for SHA/TAS, X for SHX, Y for SHY; TAS also sets SP = A&X first), and on a page cross the write address's high byte *becomes that value* — not the pre-carry high byte, not the carried one (an earlier pre-carry model passed `instr_test-v5/07-abs_xy` but was wrong; the corrected model passes it too). They are fixed 5/6-cycle stores with an unconditional pre-carry dummy read (previously a silent cycle when no page was crossed — the same realtime-DMC-clock hazard class as the Session-2 JSR/RTS fix). RDY quirk: if RDY is low during the dummy-read cycle immediately before the write (a DMC DMA serviced on that read, or a request that rose during it and is still pending — the CPU only halts at its next read, after the write), the `& (base_hi + 1)` is dropped and the raw register is stored ("SHY just becomes STY"). Detected via `CpuBus::dmc_dma_count`/`dmc_dma_pending`. Fixing this resolved all 5 AccuracyCoin UnOp_SH* tests AND `blargg_nes_cpu_test5/cpu.nes` — whose long-standing "hangs on a JAM opcode" behavior was actually the wrong-address writes smashing the test's own state; it now runs to completion and is no longer `#[ignore]`d.

**Unofficial opcode reference**: When implementing or fixing an unofficial opcode, cross-check against the expected hash in the relevant blargg ROM test rather than trusting any single written source — documented behavior varies between references.

   interrupt-polling-granularity fix (deferred NMI-edge delivery, `src/tests/integration/roms.rs`) took it
   from ~2/10 to 8/10 correct rows; the final 2 rows were fixed by modeling nesdev's
   "interrupt sequences do not perform interrupt polling" rule (`interrupt_poll_suppressed`,
   `src/cpu/mod.rs`): the interrupt handler's first instruction always executes before a
   pending interrupt that missed the T6 hijack window can be serviced. See
   `docs/cpu_interrupts.md`.

7. **`cpu_interrupts_v2/4-irq_and_dma`** — **now passes.** Three fixes: (a) `frame_reset_delay = 7` (the $4017 write is applied while the APU still sits at the start of the writing instruction, 4 cycles before the hardware write cycle, plus the hardware's 3-cycle post-write delay); (b) interrupts that first assert during a DMA stall are delivered at DMA end with one dispatch poll suppressed, so the first post-DMA instruction executes before service (`suppress_next_interrupt_poll`, mirroring the interrupt-sequences-don't-poll rule); (c) OAM DMA takes 514 cycles instead of 513 when the $4014 write lands on an odd APU cycle (`Apu::cycle_parity`).

8. **`cpu_interrupts_v2/3-nmi_and_irq`** — **now passes.** Two fixes beyond the ones above: `frame_reset_delay = 7` (see item 7), and the `$2002` read pre-advance now samples PPU state on the read cycle's final dot instead of one dot past it (`Bus::read` + `Ppu::tick_dots`). `sync_vbl` dot-locks blargg test code to VBlank onset through that read, and since a frame is a non-integer 29780⅔ CPU cycles, the one-dot sampling error only crossed a cycle boundary on this test's 2-frame delay chain — making its whole table one row early while 1-frame tests (like test 2) were unaffected. Earlier sessions' "confirmed contradiction" for this test dissolved once the source was read correctly: the NMI is a real VBL edge (not the $2000 instant-fire quirk), the NMI handler's `bit SNDCHN` acks the APU IRQ (hence `IRQ=00` rows), and rows 10-11 additionally depend on the interrupt-sequences-don't-poll rule.

9. **`cpu_interrupts_v2/5-branch_delays_irq` and the combined suite** — **now pass** (with them, all 159 blargg CPU ROM tests pass). Four fixes: (a) `$4015` reads pre-advance the APU 4 cycles so the frame-IRQ flag is sampled at the read cycle instead of the instruction's start (`APU_READ_PREADVANCE`, `src/bus.rs`; `tick_apu` repays the debt internally so total APU time is conserved); (b) an IRQ already visible at a branch's dispatch preempts the branch like any other instruction (the old dispatch-path special case is removed); (c) an IRQ-aborted branch page-fix cycle still elapses before the 7-cycle interrupt sequence (handler entry at branch T1+11); (d) the taken-branch last-clock IRQ ignore applies only to an IRQ that *first* asserts on that clock — the test harness ticks the APU per cycle and flags such assertions via `Cpu::irq_on_last_cycle`, and dispatch defers only `branch_delay_irq && irq_asserted_on_last_cycle`. Each fix was verified against a specific sub-table of the ROM's readme.

### $6000-protocol tests: all passing

The `roms.rs` harness (previously report-only for many suites) asserts every ROM's $6000 status, and all of those suites now pass. The last stragglers were fixed by open-bus modeling:

- **PPU open-bus decay register** (`Ppu::io_bus` + `open_bus()`/`refresh_open_bus()`, `src/ppu/mod.rs`): writes to any PPU register refresh all 8 bits, reads return decay-register bits for everything the PPU doesn't drive ($2002 drives bits 7-5, $2004 all, $2007 all / bits 5-0 for palette reads, write-only registers nothing), and each bit decays to 0 after ~600 ms (`OPEN_BUS_DECAY_DOTS`) without a 1-refresh. Fixed `ppu_open_bus`, `cpu_dummy_writes_ppumem`, `oam_stress`, and (with the one-byte-opcode dummy fetch below) `cpu_exec_space_ppuio`. Two adjacent fixes rode along: $2004 reads mask attribute bytes' nonexistent bits 2-4 to 0, and every one-byte opcode performs its hardware T2 dummy fetch of the following byte (`src/cpu/instructions.rs::execute`) — observable when executing out of PPU I/O space, where an RTS at $2001 must dummy-read $2002 and clear the PPU address latch.
- **CPU open-bus latch** (`Bus::cpu_open_bus`, `src/bus.rs`): every bus transfer (reads, writes, opcode/operand fetches) updates the latch — except `$4015` reads, whose status byte is internal to the 2A03 and never drives the external bus (AccuracyCoin "Open Bus" test 7; writes to `$4015` drive it like any write); reads of undriven addresses return it — $4000-$4014 and $4018-$401F entirely, $4015 bit 5, $4016/$4017 bits 5-7 (so `LDA $4016` naturally sees $40 in the top bits), and the cartridge's unmapped $4020-$5FFF expansion area (`Cartridge::read` returns `Option<u8>`; `None` = nothing drives the bus). No decay, unlike the PPU latch. Fixed `cpu_exec_space_apu`.

**Harness rule**: emulator-external inspection (the $6000 result-protocol polling, debuggers) must use the side-effect-free `Bus::peek`, never `Bus::read` — harness reads through `read` corrupt the CPU open-bus latch between the emulated program's own transfers, which `cpu_exec_space_apu` (executing from open bus) catches immediately.

`ppu_vbl_nmi/rom_singles/10-even_odd_timing` (and with it the combined `ppu_vbl_nmi.nes`) now passes. Two fixes: $2001 writes get the same 8-dots/apply/1-dot pre-advance as $2000 (previously they applied ~12 dots early, at the start of the writing instruction), and the odd-frame skipped-dot decision samples the rendering bits at the start of pre-render dot 338 — one dot earlier than the wrap check; all four of the ROM's sub-tests pin that single sample point. Since the $2001 two-tap split (see the "$2001 mask writes" design note), the skip decision taps the RAW register (`Ppu::render_raw_prev_dot`, write-cycle timing — what this ROM pinned) while the rendering pipeline sees the change `MASK_WRITE_DELAY_DOTS` later.

### Text-console tests: all passing

All 5 `sprite_overflow_tests` now pass. Sprite evaluation was rewritten as a per-dot state machine (`Ppu::evaluate_sprites`, driven on odd dots 65-255 of visible scanlines): an out-of-range sprite costs 2 dots, an in-range sprite 8 dots (4-byte copy), so the overflow flag sets at the hardware-exact dot (3.Timing). Once 8 sprites are found, the scan continues with the hardware bug — both `n` and `m` increment on out-of-range checks, misinterpreting successive bytes of successive sprites as Y coordinates (4.Obscure's diagonal scan) — and stops without wrapping when `n` walks past sprite 63. The flag only sets when a 9th in-range (possibly misread) Y is found, never merely because 8 exist (2.Details #9). The pre-render scanline no longer evaluates sprites (hardware doesn't): it just clears the evaluation state, so scanline 0 always renders with an empty sprite set, as on real hardware.

All 7 `vbl_nmi_timing` tests now pass. Three fixes: (a) the harness was switched to the shared `SystemClock` (its old hand-rolled loop never consumed the $2002-read PPU pre-advance, drifting the PPU 3 CPU cycles per read — this alone fixed `4.vbl_clear_timing` and `7.nmi_timing`); (b) the PPU's NMI is now modeled as hardware does it — a level (`vblank && nmi-enable`) edge-sampled once per CPU cycle — which yields the 2-dot NMI-suppression windows for $2002 reads and $2000 NMI-disables around VBL onset, plus the flag-never-sets race for a $2002 read 1 dot before VBL (see `src/ppu/mod.rs`, `Bus::read`/`Bus::write`); (c) the $4017 frame-counter reset delay is parity-dependent (see below).

The rest of the text-console suite passes and asserts: all 7 `vbl_nmi_timing`, `sprite_overflow_tests/1.Basics` and `5.Emulator`, all 3 `branch_timing_tests`, `cpu_timing_test6`, and both `blargg_nes_cpu_test5` ROMs (`official.nes`, and `cpu.nes` since the unstable-store fix).

### Sprite-0 hit latch delay is ~1 dot (the old 21 was harness drift)

`SPRITE0_HIT_LATCH_DOTS` (`src/ppu/mod.rs`) is 1: the flag is visible via $2002 almost immediately after the colliding pixel (valid calibration window 0-2 dots against the `sprite_hit_tests_2005.10.05` timing ROMs). The previous value of 21 was calibrated while `sprite_hit_roms.rs` used a stale run loop that never consumed the $2002-read PPU pre-advance, double-advancing the PPU 9 dots per read — the "internal pipeline delay" was compensating for that drift. `sprite_hit_roms.rs` and `ppu_roms.rs` now step via the shared `SystemClock` like every other harness; if a sprite-hit timing test ever fails after a timing change, recalibrate the constant by sweeping it rather than trusting the old 18-23 window.

### $4017 write-to-reset delay is parity-dependent

The APU frame-counter reset takes effect 3 CPU cycles after the $4017 write cycle when that cycle lands on an even APU get/put cycle, 4 when odd (`Apu::write`, `frame_reset_delay = 7 or 8`). A constant delay silently defeats blargg's `sync_apu` parity equalizer (`bit SNDCHN` / `bne`), leaving the CPU-APU parity dependent on everything executed before the sync — it only ever worked because the pre-sync frame count happened to be constant. This surfaced as `cpu_interrupts_v2/4-irq_and_dma`'s +526 row flipping (513- vs 514-cycle OAM DMA) when the VBL-read suppression race changed how many frames the shell's $2002 poll loops consumed.
